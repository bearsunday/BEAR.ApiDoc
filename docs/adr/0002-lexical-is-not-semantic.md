# ADR 0002: 名前が同じでも意味は同じとは限らない — 語彙と観測

## Status

Proposed

## Context

ADR 0001 では、パラメータ名やエンティティのプロパティから語彙（オントロジー）を取り出し、ALPS の定義に育てる構想を示した。`TermUsageIndex` はその第一歩で、API で使われている言葉（パラメータ名・スキーマのプロパティ名）を集め、同じ名前の ALPS 定義があれば対応づけて「どれだけ ALPS で説明できているか（カバレッジ）」を出す。

ただし大前提がある。**名前（綴り）が一致しても、意味が同じだとは限らない。** 特に `name`, `age`, `status` のような、どこにでも出てくる言葉で問題になる。

- **同じ名前・違う意味**: `age` は「人の年齢（年）」と「キャッシュの経過時間（秒）」では単位すら違う。`name` も、一意の ID のときと、ただの表示名のときがある。
- **違う名前・同じ意味**: `customerName` と `userName` が、実は同じものを指していることもある。

なぜ汎用語で起きるのか。**意味は「置かれた場所（型・文脈）」で確定する**からだ。schema.org が `name` を一語で回せるのは、`Person.name` と `Product.name` のように、属する型が意味を与えているから。名前単体は意味が薄く、文脈が意味を決める。だから名前の一致だけを数えたカバレッジは、ありふれた言葉ほど甘く（実態より良く）見えてしまう。

ただし、逆に振れすぎてもいけない。BEAR.Sunday / ALPS 駆動の開発では、**パラメータ名やプロパティ名は多くの場合 ALPS から採られる**（宣言が先、使用が後）。だから同名一致は「たまたまかぶった」のではなく、**多くは意図された対応（binding）**だ。ツールは文字列しか見ないので、それを *証明* はできない。だから「字句一致」と断るが、対応そのものを否定もしない——冒頭の注記は「偶然の同名」という偽陽性への保険であって、「どうせ無関係」という宣言ではない。

そして、語彙が形骸化してきた理由はいつも同じだ。立派な用語集や ontology が死んだのは、紙の上の定義と、実際の使われ方がズレても誰も気づかなかったからだ。**語彙は、使われ方から切り離された瞬間に古びて死ぬ。**

## Decision

`TermUsageIndex` は、**意味を決めつけず、使われ方を見せる**道具に徹する。

1. **名前の一致だと最初に断る** — ページ冒頭に「これは名前の一致であって、意味が同じだと証明するものではない」と必ず書く。カバレッジは「達成度」ではなく「点検の手がかり」。
2. **使われている場所を全部見せる** — どの API・どのスキーマでその言葉が出てくるかを残す。
3. **ALPS との対応は markup そのもので表す** — HTML 出力（`terms.html`）は `rel="profile"` で ALPS プロファイルを参照する。ALPS descriptor を持つ term は、その **descriptor id を `class` に担う**（microformats。alps.io が HTML 表現で示している方式）。`def` が URI ならば、term 名をその定義へのリンクにする。

   要点は、「ALPS で定義されている」という事実を **装飾バッジではなく semantic トークン（`class`）の有無で表す**こと。機械はプロファイルに照らして `class` で判別でき、人間は descriptor 由来の説明文やリンクで分かる。こうすると HTML 自体がプロファイルに対して機械可読になり、**表現と意味が一致する**。UI 制御用の class 名や見出しレベルといった、意味を持たないトークンは置かない。
4. **最後の判断は人間に渡す** — 「`name` が N か所で使われている。これは 1 つの概念か、それとも別々の N 個か？」と問いを投げる。同じものなら ALPS 定義を 1 つにして全部から参照する（本当の再利用）。違うものなら名前を分ける（`givenName` など）か、置かれた文脈で意味を区別する。

名前・リンク・`class` を付けるのは「こういう意味だ」という**主張**であって、**保証**ではない。付けて終わりにせず、主張と実際の使われ方が合っているかを見続けて、はじめて語彙は生きる。

## Consequences

### Positive

- このインデックスはソースから毎回作り直されるので、書いた意味と実際の使われ方が原理的にズレない。人間が別に「正しい一覧」を二重管理する必要がない。
- だからカバレッジが「基準」になり、変化を見張れる。実際 `testMarkdownIsDeterministic` は「前回と同じ結果か」を確かめるテストで、言葉の使われ方が変わると失敗する。これがそのまま見張りになっている。
- ALPS との対応を markup に内在させたので、**「ALPS バッジ」のような別の UI を足す必要がない**。意味は表現そのものに宿り、装飾ノイズが減る。
- 名前の一致を見るだけでも、役に立つ警告は出せる。同じ名前なのに型や形式が場所でバラバラ、ALPS の対応が減った、どこからも使われない言葉、似た名前が急に増えた、など。

### Negative / Risks

- カバレッジを「意味まで網羅できている」と誤解されるおそれ → 冒頭の断り書きでやわらげる。
- 見張りは「良い変化」と「悪い変化（退行）」を区別できないと、ただのうるさい警告になる → 基準（fixture）は、意図して変えたときに人間が更新する運用とセットにする。
- `class` に descriptor id を使うので、descriptor id が HTML の `class` / `id` として妥当である前提に乗る。ALPS の descriptor は識別子なので実務上は問題ないが、外部スキーマ由来の語は記号を含みうるため、出力側はトークンを防御的にサニタイズする（同じ姿勢は `id` 生成にも適用済み）。
- ありふれた言葉をきちんと診断するには、名前だけでなく「形（型・形式）まで見比べる」段階に進む必要がある（今後の課題）。
